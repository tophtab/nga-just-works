# R3：访问失败提示设计

## 与搁置项分离

本任务只使已经观察到的失败信息表达准确。R7 的普通解析故障、诊断开关、自动浏览器行为调整均搁置；R3 不以它们为前置任务，不实现 R7-A。

## 证据与展示

将 HTTP 状态、原有失败 kind 和有限站点原因分开保存。恢复策略继续使用原有 kind/边界；文案使用可证实事实，不由文案反推是否能切源。

| 已有证据 | 展示原则 |
| --- | --- |
| 实际 HTTP 403 | 无法访问帖子（HTTP 403） |
| 其他 HTTP/重定向状态 | 保留真实状态，提示请求失败/发生重定向，不能冒称验证 |
| 明确结构化验证码/访问验证消息 | 提示站点要求访问验证 |
| 明确结构化删除、不存在或无权限消息 | 分别说明删除、不存在或无权限 |
| HTTP 200 未知 HTML | 中性提示返回了网页内容、暂无法读取，不能推断删除或验证 |
| 无识别证据 | 保留中性失败，不猜站点原因 |

ArticleByteClient 在解码前分类 HTTP，第一版保留状态即可；不为显示“删除”去新增网页抓取、账户切换或猜测 403 正文。仅检查明确错误容器/结构化消息，不扫描正常帖文里的“删除/403”等字样。

## 数据流与兼容

ArticleFailure 扩展可选状态/原因字段，既有构造调用保留兼容。ArticleErrors.classifyHttp/bodyText/inspect 构造准确的展示信息，同时保留现有 allowsAppFallback/allowsBrowser 行为。已识别站点业务错误不能为了改变文案而变成 FORMAT。
旧链路已能识别的 HTTP/结构化错误可复用展示规则；无法解释的旧 ServerException 不在此任务中插入诊断或改写解析流程。避免新旧两层重复 toast。

## 验证与回退

合成 HTTP/HTML/业务消息覆盖 403、3xx、未知网页、明确验证、删除/不存在/权限，以及正文仅提到这些词的成功响应。验证分类与原有请求次数/切源边界不变。
撤销只影响展示证据/文案，无缓存迁移或服务端变化。与 R4 的 Presenter 改动顺序集成。
