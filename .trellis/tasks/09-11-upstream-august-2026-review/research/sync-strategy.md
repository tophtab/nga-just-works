# 后续问题：整体同步上游，还是按功能适配

## 判断

技术上可以整体合并。当前 `main@8284c703` 与上游 `master_release@22ba3082` 的共同祖先是 `5d807617`，不需要重建 Git 历史。

当前更推荐按功能选择性移植：以他的实际代码、接口和响应模型为来源，保留可复用部分，将读取/解析结果接入本 fork 的模型和调用链。是否使用 cherry-pick 是实现手段；不要求从零重写，也不能只因补丁能合并就认为功能已经兼容。

若目标改成长期紧跟上游每一版，做一次完整集成分支、解决冲突、恢复本地定制并全面验证也成立。这是比新增一个功能更大的工作。完整 merge 会记录共同的集成历史，后续 Git 合并有更清楚的基线；选择性移植则保留更小的本次范围，但以后仍需维护与上游的差异。

## 实际合并模拟

2026-09-11 使用 Git 2.43.0 的 `merge-tree --write-tree --name-only --no-messages`。该命令写入候选 Git 对象，不修改工作目录、索引或分支引用，没有实际合并代码。

比较固定提交，不包括另一个缓存/菜单任务的未提交修改。完整命令、返回值和路径见 [merge-dry-run.json](merge-dry-run.json)。

| 情景 | 方法 | 结果 |
| --- | --- | --- |
| 全部上游更新 | `main@8284c703` 与 `master_release@22ba3082` 正常三方合并模拟 | 17 个冲突路径 |
| 仅兼容模式提交 | 以 `2becba2a^ = 750871b3` 为显式三方基线，模拟向 main 应用 `2becba2a` 的单笔差异 | 7 个冲突路径；这不是已经执行 cherry-pick 的结果 |

两个命令返回 1，表示存在合并冲突，不是命令执行异常。没有评估解决冲突后的编译/运行结果；冲突文件数量也不等于工作量或缺陷数量。

整批冲突集中在：

- 根构建版本/SDK 配置。
- `AttachmentData`、`HtmlData`、图片与 BBCode decoder：与完整附件前缀及历史图床兼容交叉。
- `ForumBoardModel`、`ApiConstants`：与收藏/主页排序及图标路径交叉。
- `ArticleListContract/Presenter`、`ArticleShareViewModel`：与本地预取和页面行为交叉。
- `ArticleConvertFactory`、`FunctionUtils`、旧工具/私信 parser：上游删除或迁移了本地仍有修改的文件。

单独兼容模式的冲突涉及 Gradle、上游新 `ThreadInfoParse`、Kotlin `ForumBasicDecoder`、测试以及 `ArticleListModel/Presenter`。本 fork 缺少它假定已存在的一部分重构类型，因此它不是一笔独立的小修复。即使解决这些文本冲突，还需检查新增类的编译依赖与业务字段映射。

## 为什么当前优先选择适配

1. **有需要保留的现有行为。** 本 fork 的完整图床前缀/手动覆盖、两页预取和请求复用、收藏与主页排序不由上游统一维护。全量同步必须逐项重新对齐。
2. **上游部分改动有明确限制。** 旧接口 parser 的附件赋值晚于 HTML；备用接口缓存仍进入旧 parser；分页、空数据、回退开关、账号和图片前缀还缺完整处理。整批引入仍需我们修正这些行为。
3. **目标功能可以脱离整套重构。** 兼容模式的核心是新增读取路径和响应适配器；可以复用上游请求字段、Bean 及转换思路，映射到现有帖子模型，并保留本地缓存、图床和预取边界。

对应的详细证据分别在 [data-refactor.md](data-refactor.md)、[bugfix-browser.md](bugfix-browser.md)、[branch-and-small-fixes.md](branch-and-small-fixes.md)。
