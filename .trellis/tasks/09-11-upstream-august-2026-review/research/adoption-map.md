# 8 月改动的完整行为清单与复用方向

## 本次澄清

用户最新要求是「尽可能能使用上游的，就尽可能使用上游」，并指出先前答复没有把板块图标等其他改动讲清楚。

因此，后续方向是：**以复用现有上游实现为起点；能直接用的直接用，有本地冲突的进行适配；保留差异必须给出具体原因。** 不把未运行真实接口等同于功能不支持，也不预先将单条回复/只看某人整体排除。真正未知的字段仍不得捏造协议或声称已验证。

前面的回复把“整个 8 月的可借鉴内容”过早收窄成“兼容模式一个功能”，又把保守技术接收条件表达成首版产品限制。这是本次要纠正的说明与规划范围，并非用户已经同意舍弃其他能力。

实施前比较基线为 `5bb92cf033aa32d749d10e1a497bc05173cd2955`。规划开始时分支为fix/thread-menu-cache，最终核对时为相同提交的main，产品树没有变化。前期完整审计仍固定比较 `main@8284c703`；其后变动主要是 `6203dad5` 的菜单/缓存修复。下文保留这些比较依据，并追加实际适配状态；没有重新请求 NGA。

## 「已实现」「需适配」「仅有字段」的区别

兼容模式不是只有一个开关或空壳：上游已写 App 请求、DTO、主要楼层转换和原生显示链路，也已发送 pid/authorid。我们复用这些代码，并补足现有 reader 的分页、定位、缓存和预取衔接。

但是 `attches`、`hot_post`、`comment_to_id`、`html_head_extra` 在上游 App DTO 中只有字段声明，App parser 没有对应专门解析/展示；`vote_good/vote_bad` 也没有分数换算。这里不存在一套已经写好的完整能力可直接搬入。它们不会仅因非空而导致整页拒绝，原始数据继续保留；本轮也不从零猜出新的附件、热评或评论关系协议。

因此采用边界是：**已实现的有用能力尽量复用；必要接入适配补齐；上游没有的独立功能暂不扩建。** 缺少真实响应验证只表示可用性尚未验证，不等于上游功能未实现。详细逐字段依据见 [content-reuse-revision.md](../../09-11-thread-detail-compat-mode/research/content-reuse-revision.md)。

## 内部整理：七次重构具体整理了什么

这七个提交是同一条改造链，不是七个新界面功能：

| 内部变化 | 具体可复用内容 | 本项目的采用方向 |
| --- | --- | --- |
| Java 数据类移到 core_data 并改 Kotlin | 上游的 DTO、字段定义和 Kotlin 实现 | 新接入处尽量复用现成代码；涉及旧消费者时用适配层对接，不为类名一致整体替换 |
| 接口原始字段与楼层展示状态分开 | ThreadBean/ThreadPostBean 与 ThreadInfo/ThreadPostInfo 的职责边界 | 复用字段和转换，减少 UI 直接懂服务端字段；保留本地仍有消费者的能力 |
| parser 从 app 逐步移到 core | 用户/匿名/客户端、wrapper 处理等工具 | 复用实际可共享的函数；模块搬迁与既有迁移计划协调 |
| HTML 配置接口 | 用接口传入黑名单、签名、图片、夜间模式等配置 | 可复用接口/adapter 思路及实现，保持当前图床和设置语义 |
| 每次解析内缓存用户对象 | 同页同一作者不重复构造全部用户数据 | 可复用局部缓存；没有性能测量，不能宣称某个倍数加速 |
| 客户端类型改枚举 | 统一来源类型判断 | 可用枚举，但保留我们现有机型/系统等详细信息 |

剩下三类维护改动：

- `25652de8` 升级 fastjson2：跨网络与本地序列化的库迁移，值得单独做一批，并携带 A14/A15 等兼容案例；不是只改一行版本号。
- `4c99051f` 旧工具清理：删除不再使用的 HTML/MD5/插件/HTTP/图片辅助代码。可以复用删除清单，但先确认本 fork 的调用者，不声称有未经测量的包体/性能收益。
- `86e6e782` / `22ba3082` 发版：4.2.3、5.0.2 版本记录；后者把 compile/target SDK 升到 36。版本号沿用本 fork 发布规则；SDK 36 单独验证，保留本项目 minSdk 29，不能顺带继承上游 minSdk 30。

## 板块图标的具体区别

正文图床与板块图标不是同一条功能：正文用 read.php 的 `_ATTACH_BASE_VIEW`；板块图标用板块分类响应的 `forum_icon_pre`。

当前 `ApiConstants.java:12`、`:23` 已使用两条有效默认地址：

```text
普通板块： https://img4.nga.cn/ngabbs/nga_classic/f/app/<fid>.png
合集板块： https://img4.nga.cn/proxy/cache_attach/ficon/<stid>v.png
```

上游把普通图标的地址前缀作为服务端字段保存，普通板块拼 fid.png；合集图标将已知路径部分换成 ficon 路径再拼 stid。它不是给用户加一个新图标开关，也不是换了一套图标设计。

应复用的链是：`ForumsListBean.forum_icon_pre → 保存/校验前缀 → BoardEntity.iconUrl → UI 加载`。同时补两个可核实的适配点：

1. 上游当前只有“有新增板块”才触发合并/图标重算。只有前缀变化时也应重算和刷新，错误前缀保留可用默认。
2. 上游把根列表保存改成 HashMap 的全部节点列表，会影响层级与顺序。保留我们当前根列表持久化、收藏稳定键和主页排序，只接入 iconUrl 更新。

这两项是具体实现差异，不是以泛泛的“有风险”为理由放弃复用。

## 复用时要保留的本地能力

- 图床完整 prefix、手动选择、历史地址和音频处理：本项目比上游覆盖更多。
- 预取与前后台状态机：上游没有这条本地增强，不能整体覆盖 Presenter。
- 收藏/主页排序和板块树：不能跟随上游 map 扁平化存储而丢失。
- 客户端详细来源：上游 Toast 简化导致的信息减少没有必要复制。
- 热门回复旧字段和旧 Windows Phone 正文解码：上游重构删除了它们；当前仍保留。热门回复字段有保留能力，不等于已经存在完整热评 UI。
- 附件应在 HTML 前赋值：上游最终重构顺序有问题，应在复用代码时修正，不导入已知缺陷。

## 后续组织方式

方向改为覆盖完整行为清单，而不是只剩兼容模式：

1. **读取与正文**：兼容 API（包含 pid/authorid）、UID 楼主、引用、视频样式/标签、评论动作和缓存/账号保护，按照实际文件依赖分批接入。
2. **板块图标**：复用动态前缀及 iconUrl 模型，补刷新，并回归当前排序/收藏。
3. **内部维护**：可共享数据/解析代码随功能接入；全局 JSON 库、纯模块迁移、工具清理、SDK 36 各自按可验证批次处理。

兼容模式批次已经依据修订范围实施；其旧版“只接完整20楼页、直接排除 pid/authorid”的规划已归入 history，不再作为当前依据。其余项目继续保留在复用路线中，本清单不表示已执行全量 merge。
