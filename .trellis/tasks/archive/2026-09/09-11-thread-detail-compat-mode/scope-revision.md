# 范围修订：尽可能复用上游

## 用户最新方向

用户明确要求：「我觉得尽可能能使用上游的，就尽可能使用上游」，并要求完整解释包括板块图标在内的其他 8 月改动。

随后用户询问「上游其实还没有把这个东西做完？那我们只实现已完成的部分？」。采用边界明确为：复用源码中已实现且有价值的能力，补足接入本 fork 必需的适配；不把仅声明的可选字段包装成已实现功能，不顺带从零开发上游没有的独立功能。兼容模式主流程已存在、部分侧载字段未消费、真实接口尚未验证，是三种不同事实。

这不是批准上一版缩窄方案。上一版最终摘要和据此拟定的“完整20楼页为唯一接入范围”已被本次修订取代，不得据此启动实现。已有建任务授权继续有效，不重新询问是否建任务。

## 本任务必须调整的要求

| 原方案 | 新方向 |
| --- | --- |
| pid/authorid 场景直接跳过 App 接口 | 纳入单条回复/PID 定位、只看某人的适配目标；复用上游已传递的字段，不因入口类型预先放弃 |
| App 原生接收必须落在完整连续20楼页 | 20 是当前 UI 的假设，应由分页/定位适配处理；不能把现有 UI 限制直接当成产品排除理由 |
| attches/hot_post 等非空就整页拒绝 | 逐字段判断上游实际用法、已有 renderer 能处理的正文和附加信息；未知字段的存在本身不等于整个页面不可用 |
| 缺真实夹具作为排除功能的主要理由 | 保留源码证据和合成验证边界；缺 live 验证表示不能承诺成功率，不表示上游功能已被证明不支持 |

复用不等于忽略内容完整性：不得捏造未知附件/评论协议、静默丢失主体内容、误定位楼层、将过滤结果缓存成全帖或把错误响应当成功。具体不能解释的响应保留清楚的错误/浏览器路径；可选展示字段则局部降级。字段级研究已确认上游 App parser 未消费 attches/hot_post/comment_to_id/html_head_extra；没有“现成但被我们排除的完整附件/热评/父评论解码器”。这些未知扩展保留 raw 即可，不必另外实现一个猜测协议的功能。

仍保留的边界：上游默认关闭开关、原生 reader、现有图床/预取/缓存修复、明确账号和生命周期、错误收尾、旧缓存可读、不导入上游已核实缺陷、不擅自进行真实站点/设备测试。

## 其他 8 月改动

完整目录和解释已记录到研究任务的 [adoption-map.md](../09-11-upstream-august-2026-review/research/adoption-map.md)。它覆盖动态图标、UID 楼主、视频 CSS/标签、引用、评论菜单、缓存/账号小保护、JSON 迁移兼容、七次数据重构、工具清理及 SDK/发版。

这些都进入整体复用台账；不能再把“其他项已说明/考虑”误写成“只做兼容模式”。可独立交付的板块图标/全局库迁移等按实际依赖安排批次，不直接塞进一个未经审阅的全量 merge，也不把台账当成已经实现。
