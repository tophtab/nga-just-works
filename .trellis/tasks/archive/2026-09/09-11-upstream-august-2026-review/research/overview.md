# Justwen 上游 2026 年 8 月：做了什么，哪些值得借鉴

> 2026-09-11 后续修订：用户要求尽可能复用上游，并补全板块图标等细节。完整行为台账与最新采用方向见 [adoption-map.md](adoption-map.md)。下面保留初次审计的固定基线和当时建议；后续不能把范围继续缩成仅兼容模式，或将缺少真实夹具当作功能不支持。

## 先说结论

你记得的方向基本准确：当前 fork 采用并扩充了上游图床机制，没有跟进那组完整的数据重构或新的详情兼容模式。但不能把其余每个“修复”都当成漏掉的功能：有些我们已经独立解决，有些是在补上游重构或更换 JSON 库后才出现的兼容问题。

**8 月的主线是整理数据模型和帖子解析链，夹杂少量直接影响使用的修复，最后增加了一个默认关闭的备用详情读取接口。建议按行为挑选，保留当前 fork 已有的图床、预取、收藏排序和交互。**

优先值得考虑的，是 UID 楼主识别、视频显示/标签兼容、缓存入口及账号边界保护；动态图标前缀可作后续增强。数据分层可纳入已有迁移计划，备用 API 则需要先补完整的兼容设计和验证。

## 数据重构有什么可学的

它把原来混在 app 解析器和 Java 数据类里的东西，逐渐拆成三种职责：

| 职责 | 例子 | 为什么有价值 |
| --- | --- | --- |
| 接口原始数据 | `ThreadBean`、`ThreadPostBean` 保存 NGA 字段 | 服务端字段变化不必直接扩散到每个界面 |
| 界面要使用的数据 | `ThreadInfo`、`ThreadPostInfo` 保存正文、是否楼主、是否屏蔽等 | UI 可少处理协议细节，也便于接不同读取接口 |
| 解析与渲染 | `ThreadInfoParse`、`HtmlConvertFactory`、配置接口 | 减少 app 大类堆积，解析和设置来源更容易替换与测试 |

最适合本项目的是吸收这个方向，并入已有 `read.php` 契约任务和 Kotlin/Compose 迁移计划。上游最终仍沿用旧 MVP/RxJava 页面、可变模型和全局设置读取，不能将它当作完整的新架构。

有几个具体理由说明它还不适合整体替换：

- 新 parser 先生成 HTML，再给对象填附件列表；首次渲染拿不到那部分附件数据。
- 部分页内循环用了主题总行数，替代原来的当前页行数。
- 移除了某些原始数据/旧内容兼容，简化了客户端来源详情；这些是行为取舍。
- 当前 fork 的预取状态机、页面完整图床前缀、历史地址兼容和定制交互不在上游这套改动里。

前三项依据源码检查；没有运行上游 App 来测实际触发频率或性能。

## “避免跳浏览器”的改动有多大价值

它的思路是：`read.php` 仍为默认入口；无法解析时，经过原有重试链，再按开关尝试 `app_api.php?__lib=post&__act=list`，将另一种响应转成原生帖子页面。失败后仍可能进入内置 WebView。

这个目标有价值：尽量保留原生阅读体验。但 **兼容模式默认关闭**，本次也没有验证真实服务可用性。源码中还有几个决定移植成本的缺口：

- 新响应写入缓存后，读取缓存仍只走旧格式 parser。
- 新接口的 `perPage/currentPage` 等元数据没有完整接入旧分页和定位逻辑。
- 热评、贴条、附件、图片前缀等字段映射不完整。
- 两个回退开关都关时有遗漏的错误收尾；账号检查也有顺序问题。
- 整体替换 Presenter 会覆盖我们已有的后台预取、去重和前台接管逻辑。

因此建议把“备用数据源适配”作为独立候选，先定义正常页/空页/错误页、页码、缓存格式、账号、图床与预取边界。它不要求先搬入七次数据重构，可以适配当前模型。

## 建议的借鉴顺序

这里的优先级是收益与改动范围的判断，不是本轮已实施的功能。

| 优先级 | 建议 | 当前状态与收益 | 采用方式 |
| --- | --- | --- | --- |
| 优先小改动 | **UID 判断楼主** | 当前依赖作者名和首楼信息；UID 可改善从非首页进入时的身份判断 | 在现有模型里补主题作者 UID/降级规则，独立验证，不需要七次类型重命名 |
| 优先小改动 | **视频宽度约束、相对视频标签支持** | 当前缺 `video max-width`，也缺 `[flash]./…[/flash]` 的视频处理 | 小范围修改样式/标签规则，沿用 `NgaImageHost`，保留音频和手动图床行为 |
| 边界修复候选 | **缓存页面缺参保护、0/1 账号检查** | 当前有空参解引用和无意义重试/空账号边界 | 借鉴意图，修正上游漏 `super.onCreate` 和先取 Cookie 后检查的顺序；不扩大自动切账号 |
| 后续增强 | **动态图标前缀** | 当前图标域名已修，缺服务端迁移适应能力 | 只取前缀解析/更新；补无新增板块时刷新，保留当前根列表和排序持久化 |
| 结合既有计划 | **接口模型、展示模型、parser/渲染分层** | 长期维护价值高，即时用户功能增量小 | 纳入已有迁移切片；先有行为契约再换内部结构 |
| 单独评估 | **统一 fastjson2** | 去掉新旧库并存有维护意义，但跨网络与本地存储 | 先固化旧 JSON/偏好格式与容忍行为，再迁移 |
| 先补验证 | **备用详情读取 API** | 若能稳定工作，原生阅读收益可观；当前实现仍实验性质 | 单独设计前台适配与缓存/错误策略，不原样 cherry-pick |
| 低优先级 | **旧工具清理、SDK 36** | 清理是维护工作；SDK 是系统兼容工作 | 分别处理；没有包体/性能测量支撑，不赋予额外性能收益 |

如果只选第一轮范围，建议先看 **UID 楼主识别 + 视频显示/标签 + 缓存/账号边界**，每项都有清晰、较小的行为目标。动态图标可按使用需要排入下一轮。数据分层和备用接口都不适合作为这轮小修复的附带工作。

## 哪些已经覆盖，不必再学一遍

- 正文图床自动模式及本地扩充：已覆盖。
- 普通/合集版块改用可用的 `img4.nga.cn`：8 月 6 日已独立修复；只是没做动态前缀。
- 音频与有类型视频标签的完整附件前缀：当前实现更完整。
- 屏蔽信息在 HTML 生成前计算、评论自身头像：旧实现已有。
- `jdata` 非标准转义和上传无引号字段：当前旧库在本次合成案例中已兼容；要升级 JSON 库时再处理对应迁移要求。

最后两类最容易被宽泛的 commit 标题误导。判断依据应是“当前路径是否缺这个行为”，而不只是“Git 有没有那个 SHA”。
